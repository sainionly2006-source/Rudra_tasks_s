# P01 — Project Scope Baseline
**Project:** RE-T1 (RudraEdge Aerospace)  
**Work package date:** 22 October 2026  
**Assigned role:** Systems Requirements & Configuration Engineer  
**Prepared for:** Teacher submission  
**Document status:** Initial baseline — review and confirm against the official project description

## 1. Purpose
This document establishes an initial, traceable scope baseline for the RE-T1 training project. It identifies the assumed system boundary, intended capabilities, constraints, assumptions, and exclusions to guide requirements capture. Because the detailed project description was not included with the task-order screenshot, items marked as assumptions must be confirmed before the baseline is approved.

## 2. Project objective
Develop a clear, testable, and maintainable set of system requirements and supporting configuration records for the RE-T1 project, suitable for review, verification planning, and change control.

## 3. Scope
### 3.1 In scope
- Review the project description and identify system purpose, stakeholders, functions, and boundaries.
- Capture functional and non-functional requirements in a structured register.
- Identify performance, safety, interface, environmental, and documentation needs where applicable.
- Assign unique requirement identifiers and record rationale/source where known.
- Establish initial acceptance/verification approaches and maintain requirement status.
- Record assumptions, dependencies, constraints, open questions, and decisions.
- Maintain versioned project documentation and a change history.

### 3.2 Out of scope (unless formally added)
- Detailed hardware/software design or implementation.
- Certification, regulatory approval, or operational deployment.
- Validation of unprovided performance figures or safety claims.
- Procurement, production, or flight/field testing.
- Approval of requirements by an external customer or authority.

## 4. System context and boundary
**Working assumption:** RE-T1 is an aerospace/robotics training project requiring systems engineering documentation. The exact product, operational environment, and external interfaces are not specified in the supplied task-order screenshot.

The system boundary should be confirmed by identifying:
- Primary system and its intended users/operators.
- External systems, sensors, actuators, communication links, and power sources, if applicable.
- Physical and software interfaces.
- Operating environment and lifecycle stages.
- Applicable standards, policies, and safety constraints.

## 6. Initial high-level capabilities
These are planning-level statements, not approved product requirements:
1. The project shall maintain a uniquely identifiable set of system requirements.
2. Each requirement should be clear, singular, feasible, and verifiable.
3. Requirements should be traceable to a source and, when available, to a verification method.
4. Project assumptions, constraints, dependencies, and unresolved questions should be documented.
5. Changes to baselined requirements and documents should be recorded and reviewed.
6. Deliverables should be readable, version-controlled, and suitable for review.

## 7. Constraints
- The 22 October 2026 task order calls for a project scope baseline and an initial requirements register.
- Requirements must not be presented as confirmed customer requirements unless supported by an approved source.
- Any numeric performance, safety, environmental, or interface limits must be sourced or explicitly marked TBD.
- Files should use stable names and revision identifiers.

## 8. Assumptions
- The project code is RE-T1, based on the supplied task-order screenshot.

## 9. Dependencies and open questions
- What is the exact RE-T1 system/product and intended mission?
- Who is the customer, operator, and approving authority?
- Which operational scenarios and environments must be supported?
- Are there mandatory standards, safety rules, or regulatory constraints?

## 10. Acceptance criteria for this baseline
- Scope, exclusions, assumptions, and open questions are documented.
- Candidate requirements have unique identifiers.
- Requirements are written in testable language where possible.
- Unknown values are marked TBD rather than invented.
- The project owner/reviewer has an opportunity to confirm the baseline.
